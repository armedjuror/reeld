# reeld — Spec v1

Personal reel production suite for Ajwad. Single user, runs locally on a MacBook, built so it can become multi-user later.

Living version: [reeld — Spec v1](https://claude.ai/artifact/MGgm3Dywck1ThSTJbhQ9wd). This file is the repo copy for coding sessions; keep the two in sync.

## 1. Goals

- Cut Ajwad's time per reel to two touchpoints: approving the script and recording the voiceover.
- Cover the whole loop: series design → scripts → recording → edit → publish → insights → analysis → better scripts.
- Run all LLM work through Claude Code (`claude -p`), not the API, for now.
- Stay ready for multi-user: a user ID on every record, a swappable model layer, and per-account tokens.

### Not in scope for v1

- Native comment auto-replies (SuperProfile handles DMs).
- Native Instagram publishing (SuperProfile handles scheduling).
- Public app, billing, Meta app review.

## 2. Stack

- FastAPI web app with SQLAlchemy 2 + Alembic on Postgres, plus Celery workers and Redis, running locally. The suite lives in `suite/` beside the legacy FastAPI reel editor (`main.py`) and shares its database and `users` table.
- A `claude -p` runner service: each stage calls Claude Code with an explicit, minimal context bundle and an MCP config.
- Local speech: the MMS forced aligner (torchaudio) for script-to-audio alignment; IndicWhisper for free transcription when needed.
- ffmpeg for cutting, loudness normalisation and the BGM/SFX mix.
- Visuals are generated by Claude directly, as with the Ballot Math edits. No Manim.
- Integrations: the SuperProfile MCP (publishing, Auto-DM), the Meta Graph API (reel insights), and GitHub (blog pushes to armedjuror.github.io).
- reeld's own MCP server (`suite/mcp_server.py`), so Claude chats can create and update series inside the app.

## 3. Context hierarchy (the key design)

Every stage builds its prompt from small layered records. Lower layers override higher ones, section by section (`## Heading` blocks).

1. **User voice profile**: narration style, tone, language habits, how he addresses viewers, banned phrases, brand defaults (palette, mascot, fonts), default CTA style. Fed to every stage that writes or designs.
2. **Series bible**: audience, purpose, format, length, language, tone overrides, visual overrides, CTA pattern. Anything stated here wins over the user profile.
3. **Episode line**: the single plan row for this episode. It can carry one-off overrides, such as a longer runtime.

The resolver (`suite/context.py`) merges these into one compact `context.md` per stage run and logs exactly what was sent (document versions and a token estimate), which keeps token use predictable and debuggable.

## 4. Series package (what Claude produces when shaping a series)

When a series is designed in a Claude chat, Claude pushes this package to reeld through the reeld MCP. It is stored as DB rows, never files.

| Record | Purpose | Loaded by |
| --- | --- | --- |
| bible | Identity of the series (under one page) | Every stage, merged into the profile |
| plan | One line per episode: number, title, core idea, hook, comment keyword, slot, overrides | Only the current line, plus neighbours for continuity |
| skill `script` | How to research and write an episode | Research and script stages |
| skill `rubric` | Checkable quality criteria | Critic stage |
| skill `visuals` | Scene and illustration rules | Visual stage |
| skill `auto-<name>` | One per automation (blog case study, PDF deliverable, etc.) | That automation only |
| automations | Which automations run per episode, their order and targets | Pipeline |
| continuity | `## Ep N` entries: covered, promised, callbacks | Script stage (last 5 only) |
| learnings | Capped list of distilled rules from edits and analysis | Script and critic stages |

Token rules:

- No stage ever loads full past scripts. Continuity comes from the continuity record.
- Learnings have a hard cap (for example 40 rules). When full, the distil step merges rules instead of appending.
- Shared skills (brand visuals, audio rules) live once at user level and are referenced, not copied.

## 5. Episode pipeline

Each episode's stage outputs are versioned records, so any stage can be rerun on its own.

1. **Brief**: resolve the context bundle from the user profile, bible, episode line, continuity and learnings.
2. **Research note**: concise, cited, at most three pages. It doubles as the source for deliverables.
3. **Script**: writer pass, then a critic pass in a fresh context against the rubric. Up to three revise rounds; failures surface flagged. **Gate 1: Ajwad approves or edits.** The before/after of his edits is saved.
4. **Record**: Ajwad records, keeping retakes in one take.
5. **Audio**: forced alignment against the approved script, keep the last clean take of each line, cut silences and fillers, normalise loudness. **Gate 2: quick listen and approve.**
6. **Visuals and edit**: Claude produces the scene plan and the visuals from the aligned script; BGM and SFX come from the approved library; ffmpeg renders the final cut.
7. **Automations**: run what the series' automations list, for example the blog case study (markdown → commit → push → URL), the comment deliverable PDF, the post copy (caption, hashtags, CTA, links), and the continuity update.
8. **Publish**: through the SuperProfile MCP, schedule the reel and create its keyword Auto-DM with the deliverable.

## 6. Insights and analysis

- **Daily pull on app open**: fetch insights for all live reels from the Meta Graph API (views, reach, likes, comments, shares, saves, average watch time). The analysis agent runs in parallel.
- **Meta access**: a free Meta developer app in development mode, linked to his own Instagram professional account; no app review needed. The long-lived token is stored and refreshed automatically before it expires (about every 60 days).
- **Analysis skills**: per-episode (what worked against the series' own baseline), series-level (trends across episodes, hook and topic performance), and account-level.
- **Output 1, insights for Ajwad**: a short daily digest in the app.
- **Output 2, proposed changes**: suggested edits to learnings, the rubric, the plan or the bible, shown as diffs. **Nothing is applied without one-click approval.** Single-reel results are treated as noise; changes need a pattern across several episodes.
- **Edit distillation**: every ten approved scripts, his edits are distilled into proposed learnings, through the same approval flow.

## 7. UI

The UI is task-oriented, not video-oriented. On login Ajwad never has to work out what needs doing: the app lists his tasks, and he just completes them one by one. Series and episodes are where the tasks come from, not where he goes looking for work.

- **Home = My tasks**: a single ordered list of everything that needs him, across all series. Each task has a type, the episode it belongs to, an estimated time and one button that opens exactly the screen needed to finish it.
    - Task types: approve script, record episodes (batched), check audio, approve video, review a skill-change proposal, read today's insights, fix a failed stage.
    - Order: whatever unblocks the publishing schedule soonest comes first; tasks that share a mode are grouped (for example "Record 3 episodes, about 12 min").
    - Finishing a task moves the pipeline on automatically and drops the next task into the list. An empty list means nothing is waiting on him.
- **Focused task screens**: each opens with only what that task needs. Approve script = script plus critic notes and Approve / Edit. Record = teleprompter mode with one-tap takes, running through every queued episode. Check audio = player with cut markers and Approve. Proposal = diff plus Accept / Reject.
- **Today header**: the plan for today at a glance (tasks left, reels scheduled, the daily insights digest in two or three lines).
- **Series board** (secondary): one card per episode moving through Script → Record → Edit → Publish → Live, for when he wants the overview, not for daily work.
- **Settings**: the user voice profile, the BGM/SFX library, and integrations (SuperProfile, Meta, GitHub).

### Calendar

Every episode has a publish slot that is either precise (a date, optionally a time) or vague (a week, a month, or just "after Ep 4").

- **Calendar view**: precise slots sit on their day; vague ones sit in a band across their week or month.
- **Today / Tomorrow**: the home screen opens with two short strips showing the precise-dated episodes due to publish and anything that must be done for them. Vague episodes never appear there.
- **Deadlines drive tasks**: for a precise slot, the app works backwards (publish → edit → audio → record → script) and raises each task early enough, with its due date shown. Tasks behind schedule are flagged at the top.
- **Firming up**: turning a vague slot into a precise date is a quick action on the calendar, and the backward-planned tasks appear at once.

## 8. Data model

Implemented in `suite/models.py` (tables prefixed `suite_`).

- `User`: the legacy `users` table, shared with `main.py`.
- `Document` + `DocumentVersion`: every piece of text, scoped to a user, series or episode, with immutable versions (voice, bible, skills, continuity, learnings, research, script, scene plan, automation outputs).
- `Series`: belongs to a user; holds name, status and the automations list.
- `Episode`: belongs to a series; holds its plan line, slot, overrides and pipeline state.
- `StageRun`: one row per step execution, with the context manifest, output version, Claude session ID, `resume_at` and status.
- `Task`: something that needs the user; generated when a stage reaches a gate or fails.
- `Proposal`: a suggested change to a series document, with its source and status.
- `InsightSnapshot`: stats per episode per pull.
- `MediaAsset`: storage key and metadata for audio, video and library files.

## 9. Storage: database first

The database is the only source of truth, so moving off the MacBook later is a config change, not a rewrite.

- **Text lives in Postgres**: all of the documents above, plus stats, proposals and tasks. Every edit creates a new version row, which also gives history and diffs for free.
- **Media goes through a storage abstraction** (`storage.py`): raw takes, cleaned audio, rendered videos, the BGM/SFX library. Local disk now, S3 later, by changing settings only. The DB holds only the keys and metadata.
- **Claude Code runs on a temporary workspace**: before each step the runner materialises the needed records into a throwaway directory (`ResolvedContext.materialise`), runs `claude -p` there, then ingests the outputs back into the DB and deletes the directory. Nothing in it is ever read again.
- **reeld MCP writes straight to the DB**: pushing a series from a Claude chat creates records, never files.

## 10. Claude Code limit handling

A usage-limit hit pauses work and resumes it automatically, losing at most the step in progress.

- **Small checkpointed steps**: long stages are split into steps (research, draft, each critic round, scene plan, each automation). Each step's output is saved before the next starts; finished steps never rerun.
- **Detection**: every `claude -p` call runs with JSON output, so the runner gets the session ID and a clear error. A usage-limit error is told apart from ordinary failures.
- **Pause**: the `StageRun` is marked paused with the session ID and a `resume_at` time parsed from the error (fallback: retry with backoff). A Celery task is scheduled for just after the reset.
- **Resume**: the step continues with `claude --resume <session id>`; if the session can't be resumed, the step restarts from its last checkpoint.
- **Queue awareness**: while paused, no new Claude steps start; non-Claude work (audio, ffmpeg renders, insight pulls) carries on.
- **UI**: shown as "Paused until 16:30, resumes automatically". It creates no task unless a resumed step fails again.

## 11. Build order

All seven steps are built in `suite/` (see LOCAL_TESTING.md for what was verified where):

1. Series package import through the reeld MCP, plus the context resolver.
2. Script stage with the critic loop and Gate 1.
3. Audio stage with alignment and Gate 2.
4. Visual and edit stage.
5. Automations runner (blog first).
6. SuperProfile publishing.
7. Meta insights pull and the analysis agent with proposals.

Implementation notes that refine the spec:

- Audio: the recording style is "pause between lines, repeat a line after a slip". Utterances are split on silences and matched to script lines with MMS forced alignment (`requirements-ml.txt`); the last matching take wins. Without the speech model the stage only removes silences.
- Publishing falls back to a manual "Post" task (caption, DM text, video) when SuperProfile isn't enabled or the video has no public URL. Episodes with an "after Ep N" slot wait until Ep N is live.
- Every LLM step stores its cost; the episode view shows it per step.
